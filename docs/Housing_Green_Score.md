# 공공임대 단지 × 녹지 접근성 (Green Score)

공공임대 단지를 후보로 두고, 각 위치의 녹지 접근성을 정량 점수로 제시하여
주거 선택을 지원하는 기능의 설계 문서.

기존 분석이 **행정동/자치구 단위 통계**였다면, 본 기능은 **개별 좌표 단위**로 내려가
"이 위치에 살면 공원 접근성이 어떤가"를 답한다.

---

## 배경

| 근거 | 내용 |
|------|------|
| 2040 서울도시기본계획 | 보행 10분(약 800m) 이내 공원 접근권 확보 |
| 도시공원 및 녹지법 | 1인당 공원녹지 6m²/인 |

민간 매물 데이터는 플랫폼 소유 자산이라 합법적 확보가 어렵다.
반면 공공임대 단지 정보는 공개 데이터로 제공되며, 청년·신혼부부의
공공임대 지원 시 단지 비교 수요가 뚜렷해 대상으로 적합하다.

### 데이터 출처

| 데이터 | 출처 | 형식 |
|--------|------|------|
| SH 주택관리현황 | 서울열린데이터광장 (OA-12027) | xlsx, 연 1회 갱신 |
| SH 주택관리현황 | 공공데이터포털 (15133405) | csv, 약 700건 |
| LH 전국 아파트 단지정보 | 공공데이터포털 (15080989) | csv (전국 확장 시) |

주요 필드: 자치구, 단지명, 주소, 우편번호, 주택유형, 세대수, 입주개시일
**좌표가 없으므로 주소 → 좌표 지오코딩이 선행되어야 한다.**

---

## 데이터 흐름

```
SH/LH 단지 파일 → 주소 지오코딩 → 좌표 확보
                                    ↓
                  parks 테이블(공원 좌표)과 거리 계산
                                    ↓
                  단지별 녹지 점수 사전 계산 → DB 적재
                                    ↓
                  API는 조회만 수행 (요청 시점 계산 없음)
```

무거운 연산은 전부 적재 시점에 끝낸다. 조회는 사전 계산된 값을 읽기만 한다.

---

## 테이블 설계

### `housing` — 단지 원본 정보

| 필드 | 타입 | 설명 |
|------|------|------|
| `id` | SERIAL PK | |
| `source` | VARCHAR(10) | `SH` / `LH` |
| `complex_name` | TEXT | 단지명 |
| `gu_code` | VARCHAR(5) FK | districts 참조 |
| `address` | TEXT | 원본 주소 |
| `lease_type` | TEXT | 영구임대/국민임대/행복주택/장기전세 등 |
| `households` | INTEGER | 세대수 |
| `lat`, `lng` | DOUBLE PRECISION | 지오코딩 결과 |
| `geocode_status` | VARCHAR(10) | `ok` / `failed` |

### `housing_green_score` — 계산된 점수

| 필드 | 타입 | 설명 |
|------|------|------|
| `housing_id` | INTEGER PK FK | housing 참조 |
| `park_count_800m` | INTEGER | 반경 800m 내 공원 수 |
| `park_area_800m` | DOUBLE PRECISION | 반경 800m 내 공원 총면적 |
| `nearest_park_id` | INTEGER FK | 최근접 공원 |
| `nearest_park_dist_m` | DOUBLE PRECISION | 직선거리 |
| `nearest_park_walk_m` | DOUBLE PRECISION | 실제 도보거리 (지연 계산) |
| `nearest_park_walk_sec` | INTEGER | 도보 소요 시간 |
| `access_score` | DOUBLE PRECISION | 접근성 (0~100) |
| `sufficiency_score` | DOUBLE PRECISION | 충분성 (0~100) |
| `diversity_score` | DOUBLE PRECISION | 다양성 (0~100) |
| `green_score` | DOUBLE PRECISION | 종합 (0~100) |
| `policy_met` | BOOLEAN | 도보 800m 내 공원 존재 여부 |
| `computed_at` | TIMESTAMP | |

### 두 테이블로 분리하는 이유

지오코딩은 외부 API 호출이라 재실행에 비용과 시간이 들지만,
점수 재계산은 DB 내부에서 끝난다.
점수 산식은 앞으로 여러 번 조정될 가능성이 높으므로,
**재수집 없이 재계산만 가능한 구조**가 실질적 이득이 된다.

## 녹지 점수 산식

단일 숫자만 제시하면 "왜 이 점수인지" 설명되지 않아 블랙박스가 된다.
의사결정 지원의 핵심은 근거 제시이므로 **3개 축을 각각 노출**하고,
종합 점수는 정렬·필터 용도로만 사용한다.

### ① 접근성 (Accessibility)

가장 가까운 공원까지의 거리 기반.

| 거리 | 점수 |
|------|------|
| 250m 이하 | 100 |
| 250m ~ 800m | 100 → 50 선형 감소 |
| 800m ~ 1600m | 50 → 0 선형 감소 |
| 1600m 초과 | 0 |

정책 기준선인 **800m가 정확히 50점**이 되도록 설계했다.
기준 충족 시 50점 이상, 미달 시 50점 미만이라 직관적으로 읽힌다.

### ② 충분성 (Sufficiency)

반경 800m 내 공원 총면적을, **서울 전체 단지 분포에서의 백분위**로 환산.

법정 기준(1인당 6m²/인)을 직접 적용하지 않는 이유는, 반경 800m 내 인구를
추정해야 하는데 `population` 테이블이 행정동 단위라 오차가 크기 때문이다.
억지로 절대 기준을 만드는 것보다 상대 위치가 정직하다.

### ③ 다양성 (Diversity)

반경 800m 내 `parks.park_type`(공원구분)의 고유 종류 수.

| 종류 수 | 점수 |
|---------|------|
| 1종 | 25 |
| 2종 | 50 |
| 3종 | 75 |
| 4종 이상 | 100 |

근린공원급 이상이 하나도 없으면 상한 50으로 제한한다.
어린이공원 3개보다 근린공원 1개 + 어린이공원 1개가 생활 만족도가 높다는 판단.

### 종합

```
green_score = 0.5 × 접근성 + 0.3 × 충분성 + 0.2 × 다양성
```

별도로 `policy_met`(불리언)을 제공한다 — "도보 10분 내 공원 접근권 ✓/✗".
점수와 무관한 2040 계획 기준의 이진 판정이라 가장 설득력이 높다.

> **미확정**: 가중치 0.5 / 0.3 / 0.2 는 잠정값이며 검토 필요.

## 거리 계산 — 2단계

화면 단계와 계산 정밀도를 맞춘다.

### 1단계 — 직선거리 (사전 계산, 전량)

- 하버사인 공식, numpy 벡터 연산
- 단지 1,000개 × 공원 1,724개 ≈ 170만 쌍도 수십 ms 수준
- 용도: 반경 800m 내 공원 집계, 최근접 공원 탐색, 점수 산출
- **목록/지도/랭킹 화면은 전부 이 값으로 즉시 응답**

### 2단계 — 실제 도보거리 (지연 계산, 선택적)

- Google Directions API (walking mode)
- 단지 상세 조회 시점에 호출하고 결과를 DB에 캐시 → 두 번째부터 무료
- 전량 사전 호출(약 3,000콜)하지 않는 이유는 실제로 상세까지 보는 단지가 일부이기 때문

### 2단계가 필요한 이유

직선 800m와 실제 보행 800m는 하천·철도·대로 때문에 크게 어긋난다.
"직선 500m인데 다리를 돌아가야 해서 실제로는 도보 15분"인 경우를 잡아주는 것이
본 서비스의 차별점이 된다.

## API

| 엔드포인트 | 설명 |
|------------|------|
| `GET /api/housing?gu=&type=&min_score=` | 단지 목록 + 점수 (필터) |
| `GET /api/housing/{id}` | 상세 + 반경 내 공원 목록 + 점수 분해 |
| `GET /api/housing/{id}/walk` | 실제 도보 경로/시간 (지연 계산, 캐시) |
| `POST /api/green-score` | **임의 좌표**의 녹지 점수 |

### `POST /api/green-score` 의 위치

이 엔드포인트가 기능의 코어다. 좌표 하나만 있으면 점수가 나오므로
**공공임대 단지가 아니어도** 사용자가 지도를 클릭하거나 주소를 입력하면 동작한다.

공공임대 데이터는 "후보를 쉽게 찾아주는 레이어"일 뿐이며,
따라서 외부 데이터 확보가 지연되어도 코어 기능은 막히지 않는다.

---

## 프론트엔드

기존 구조(지도 + 사이드바 + 레이어 토글)를 유지한다.

- 레이어 토글에 "공공임대 단지" 추가
- 단지 마커 클릭 → 사이드바에 점수 카드 (기존 공원/구 클릭 패턴과 동일)
- 지도 빈 곳 클릭 → 해당 좌표의 녹지 점수
- 필터: 자치구, 임대유형, 최소 점수

### 부수 효과 — 마커 성능 문제 해소

현재 공원 마커 1,724개를 서울 전역에 동시 렌더링하면서 성능 문제가 있다.
본 설계에서는 **"선택된 단지 반경 800m 내 공원"만** 그리면 되므로
통상 5~15개 수준으로 줄어든다. 클러스터링도, 배치 추가 최적화도 불필요해진다.

## 구현 순서

| 단계 | 내용 |
|------|------|
| 1 | SH 주택관리현황 확보 → 주소 정제 + 지오코딩 → `housing` 적재 |
| 2 | 하버사인 반경 집계 + 최근접 계산 → `housing_green_score` 적재 |
| 3 | API 엔드포인트 4개 추가 |
| 4 | 프론트 단지 레이어 + 점수 사이드바 |
| 5 | Directions API 도보거리 (지연 계산) |

---

## 미확정 사항

- **점수 가중치** — 0.5 / 0.3 / 0.2 유지 여부
- **지오코딩 제공자** — 카카오 로컬 API(무료 일 30만건, 정확도 우수) vs V-World(국토부, 공공성 부합하나 주소 정제 품질 아쉬움). 카카오 권장.
- **대상 범위** — 서울(SH)만으로 시작할지, LH까지 붙여 전국으로 확장할지. 프로젝트가 서울 대상이므로 서울 우선 권장.
